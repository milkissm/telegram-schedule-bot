# Как участвовать в проекте

Документ описывает минимум, без которого совместная работа разваливается:
как называть ветки и коммиты, что проверять перед отправкой кода, как оформлять
pull request. Правила действуют для всех, включая тех, кто делает документацию.

Главное правило: **в `main` напрямую не работаем.** Любое изменение проходит
через отдельную ветку и pull request.

---

## 1. Один раз после клонирования

Установить зависимости и локальные проверки:

```bash
pip install -r requirements.txt
pre-commit install
```

Вторая команда создаёт файл `.git/hooks/pre-commit` — скрипт, который git
запускает сам перед каждым коммитом. Она выполняется **на каждой машине
отдельно**: файл хука не хранится в репозитории, поэтому у того, кто команду
не выполнил, проверки не работают.

Если `pre-commit` не устанавливается с ошибкой про `PyYAML` и компилятор —
значит используется Python 3.15, для него ещё нет готовых пакетов. Установите
инструменты на Python 3.13:

```bash
py -3.13 -m pip install "pre-commit>=3.6,<4.0"
py -3.13 -m pre_commit install
```

Дальше вместо `pre-commit ...` используется `py -3.13 -m pre_commit ...`.
Коммиты это не затрагивает: в файле хука прописан полный путь к интерпретатору.

---

## 2. Требования к окружению

| Компонент | Версия | Примечание |
|---|---|---|
| Python | **3.13** | 3.15 пока не поддерживается инструментами разработки |
| PostgreSQL | 15+ | см. константы, К1 |
| git | 2.40+ | |

Версия Python в проекте — 3.10 и выше, но разработка ведётся на 3.13:
для неё есть готовые пакеты у всех зависимостей.

## 3. Ветки

Перед созданием ветки забрать актуальный `main`:

```bash
git checkout main
git pull origin main
git checkout -b chore/project-structure
```

Имя ветки: `тип/краткое-описание`, латиницей, слова через дефис.

```text
feat/upload-schedule
fix/week-parity
docs/tech-stack
chore/database-setup
```

Типы те же, что у коммитов (раздел 4). Ветка живёт до мержа pull request,
после мержа удаляется.

---

## 4. Коммиты

Формат сообщения:

```text
тип: что сделано
```

Правила:

- тип — из таблицы ниже, строчными буквами;
- после двоеточия — с маленькой буквы, в прошедшем времени;
- точка в конце не ставится;
- один коммит — одна логическая правка. «Добавил парсер и поправил README» — два коммита.

| Тип | Когда использовать |
|---|---|
| `feat` | новая функциональность |
| `fix` | исправление ошибки |
| `docs` | документация |
| `chore` | инфраструктура, зависимости, настройки |
| `refactor` | переделка кода без изменения поведения |
| `test` | тесты |

Примеры:

```text
feat: добавлен парсер файлов расписания
fix: исправлен расчёт чётности недели
docs: описан сценарий напоминаний
chore: настроены pre-commit хуки
```

Плохие сообщения: `update`, `fix`, `правки`, `ещё немного`, `WIP`.

---

## 5. Проверки перед коммитом

Если хук установлен, `git commit` сначала запускает проверки. Что они делают:

| Крючок | Что проверяет |
|---|---|
| `trailing-whitespace` | убирает пробелы в конце строк |
| `end-of-file-fixer` | добавляет перевод строки в конец файла |
| `check-yaml` | синтаксис YAML (конфиги, workflow-файлы) |
| `check-merge-conflict` | не даёт закоммитить маркеры конфликта |
| `ruff-check` | ошибки кода: неиспользуемые импорты, неопределённые имена |
| `ruff-format` | единое форматирование: отступы, кавычки, пробелы |

Ручной прогон по всем файлам:

```bash
pre-commit run --all-files
```

**Если хук исправил файлы**, коммит отменяется, а в выводе написано
`files were modified by this hook`. Это нормальное поведение, а не ошибка:
повторите

```bash
git add -A
git commit -m "то же сообщение"
```

Второй раз коммит проходит.

**Флаг `--no-verify` не используем.** Он отключает проверки и пропускает
в `main` код, который сломает сборку у остальных. Если хук мешает — чините
код или конфиг, а не обходите проверку.

## 6. Pull request

Отчёт по задаче — это pull request, а не сообщение в чат и не отдельный файл.

В описании:

1. что сделано — по пунктам;
2. как проверить — конкретные команды, которые ревьюер выполнит у себя;
3. на что смотреть — неочевидные решения, изменённые чужие файлы.

Шаблон подставляется автоматически из `.github/pull_request_template.md`.
Описание должно быть понятно человеку, который не участвовал в задаче.

**Одобрения:** мерж возможен после минимум одного одобрения, норма — три.
Если правка затрагивает общий код или конфиги, дождитесь трёх.

**Перед отправкой на ревью:**

- [ ] ветка создана от свежего `main`;
- [ ] `pre-commit run --all-files` проходит без замечаний;
- [ ] в коде нет токенов, паролей и содержимого `.env`;
- [ ] новые файлы и папки добавлены в `docs/design/architecture.md`;
- [ ] ветка не содержит чужих коммитов.

---

## 7. Если что-то не работает

| Симптом | Причина и решение |
|---|---|
| `pre-commit: command not found` | пакет не установлен или не в `PATH`. Используйте `python -m pre_commit ...` |
| Ошибка сборки `PyYAML` при установке | Python 3.15 — используйте 3.13 (раздел 1) |
| Хук правит файлы при каждом коммите | файлы не добавлены в индекс: `git add -A` перед коммитом |
| Хук не запускается совсем | не выполнен `pre-commit install` на этой машине |
| `ruff` ругается на длину строки | лимит 100 символов, настройка в `pyproject.toml` |

## 8. Документация

Документация лежит в `docs/`:

| Папка | Содержание |
|---|---|
| `docs/requirements/` | роли пользователей, пользовательские истории |
| `docs/design/` | архитектура, интерфейс, сценарии диалогов, стек |
| `docs/diagrams/` | диаграммы (исходники `.drawio` и экспорт `.png`) |

Изменения в документации проходят тот же путь: ветка → коммит → pull request.
Диаграммы правятся в `.drawio` и экспортируются в `.png` в том же PR, иначе
картинка и исходник разойдутся.
